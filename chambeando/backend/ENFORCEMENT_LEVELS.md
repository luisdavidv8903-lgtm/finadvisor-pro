# Enforcement Levels — Chambeando Backend

Every protection claim made about this backend (in this doc, in code comments, or in prior phase reports) falls into exactly one of these buckets. **A claim in a weaker bucket than stated here is an overstatement and should be corrected wherever found** — this document exists because Phase 2B's report used language ("structurally incapable", "sole writer", "append-only") that was true at the *application* level but was not always clearly distinguished from DB-level or test-level guarantees. This phase (2B.1) re-audits those claims.

**DB-ENFORCED** — the database engine itself rejects the violation, regardless of which code (or which bug, or which ad-hoc script run against the same credentials) attempts it.
**APPLICATION-ENFORCED** — the FastAPI/SQLAlchemy application layer rejects it (a `require_role` check, a service function's guard clause, a Pydantic schema). Something with direct DB access, bypassing the app, is *not* stopped.
**TEST-ENFORCED** — no engine or application guard exists; a test currently catches a regression if the invariant breaks, but nothing prevents new code from reintroducing the violation.
**CONVENTION ONLY** — documented expectation, not verified by anything automatic.

| "All application timestamps are UTC instants; every DateTime comparison compares the same instant regardless of dialect" (Phase 2B.5) | *previously undocumented — 19 columns were bare `DateTime`, naive* | **APPLICATION-ENFORCED + TEST-ENFORCED**, dialect representation differs — **NOT uniformly DB-ENFORCED**. | All 19 `DateTime` columns are now `DateTime(timezone=True)`. On **PostgreSQL** this is a genuine DB-level representation guarantee (native `TIMESTAMP WITH TIME ZONE`, confirmed empirically: `information_schema.columns` shows `timestamp with time zone`, and a round-trip returns `tzinfo=UTC` — `test_datetime_round_trip_preserves_utc_instant`, POSTGRES_VERIFIED). ## What this means practically

- Trust the **DB-ENFORCED** rows even if application code has a bug.
- Trust the **APPLICATION-ENFORCED** rows only as far as you trust every code path that touches the DB with the app's credentials — a future admin script, a debugging session, or a bug could bypass them. This is normal for a backend at this stage, but it's why production hardening (separate DB roles, triggers) is listed as a blocker-before-real-money, not optional polish.
- **TEST-ENFORCED** rows will regress silently if a future change removes the guard and nobody notices the test failure (or nobody runs the tests). They are real protection today, contingent on the test suite actually being run in CI before deploy — which does not exist yet in this repo (no CI config was set up in any phase so far).
